# weather_chart_vlm — 天気図VLM解説

詳しくは [MANUAL.md](MANUAL.md)（運用マニュアル）を参照。

気象庁の地上天気図・衛星画像をVLM（Vision-Language Model）に読ませ、気圧配置を判定して平文で解説するプロジェクト。
データはすべて気象庁（公開）。個人データは不使用。出典: 気象庁ホームページ。

> 元は [weather_hackathon_ideas](https://github.com/masauehr/weather_hackathon_ideas)（気象×生成AIハッカソン事前準備）のアイデア ID-32 として検証したもの。検証がGOだったため独立プロジェクトとして切り出した（2026-09-29）。

**画像一覧と読み解き → [CHARTS.md](CHARTS.md)**（天気図2枚・赤外1枚を [images/](images/) に同梱し、要素ごとに解説）
**発表スライド（Marp） → [SLIDES.md](SLIDES.md) / [SLIDES.pdf](SLIDES.pdf)**
**デモUI → [webui/](webui/)**（実測データを使った静止デモ。読者切替・ガードレール検証パネルつき。`python -m http.server` で`webui/index.html`を開くだけで動く）
**常時公開 → <https://masauehr.github.io/weather_chart_vlm/webui/index.html>**（GitHub Pages。毎朝8:45 JST頃に自動更新、直近10日分の履歴を日付選択で切替可能）

## 毎日の自動更新（GitHub Actions）
[.github/workflows/daily-update.yml](.github/workflows/daily-update.yml) が毎朝8:45 JST（23:45 UTC）に [daily_update.py](daily_update.py) を実行する。
1. `fetch_chart.py` で今日の天気図・衛星・アメダス・予報を取得
2. Claude API（Sonnet 5）で気圧配置を判定（一般向け・こども向けの解説を1回の呼び出しで取得）
3. `validate.py` のガードレール検証
4. [webui/history/<日付>/](webui/history/) に画像＋data.jsonを保存、**10日より古い履歴は自動削除**
5. GitHub Actionsがpush → GitHub Pagesが自動再ビルド

**セットアップに必要な作業（本人のみ）**: リポジトリの Secrets に `ANTHROPIC_API_KEY` を登録する必要がある（Claude Codeからは`.env`の内容を読めないため、以下はご自身で実行）。
```bash
gh secret set ANTHROPIC_API_KEY --repo masauehr/weather_chart_vlm
```
GitHub Actionsは**公開リポジトリでは無料**（標準ランナーに分数制限なし）。かかるのはClaude APIの呼び出し分のみ（1日あたり約$0.02〜0.04）。
動作確認は Actions タブから `workflow_dispatch` で手動実行できる。

> 補足: cronは毎時0分ちょうど（`0 21 * * *`）だとGitHub側の混雑で遅延・スキップされやすいため、`45 23 * * *`のように数分ずらしている（なお2026-10-01朝は6:13の定時実行が走らなかったため、8:45に変更）（weather_hackathon_ideas での運用時に実際に発生した不具合の教訓）。

## VLM とは
**VLM（Vision-Language Model、視覚言語モデル）** は、画像とテキストの両方を入力に受け取り、テキストで答えるAIモデル。

| | 入力 | 出力 |
|---|---|---|
| LLM | テキストのみ | テキスト |
| VLM | 画像 ＋ テキスト | テキスト |

- 写真・グラフ・スクリーンショット・天気図などを見て「何が写っているか」「何が読み取れるか」を言葉で答える。Claude は画像対応のため VLM として使える。
- **このプロジェクトでの役割**: 天気図・衛星画像とアメダス実況（テキスト）を一緒に渡し、①高気圧・低気圧・前線・台風の位置と気圧配置の型の判定、②「なぜこの天気か・明日どうなるか」の平文解説、を出させる。天気図は等圧線・前線記号・示度が密に描かれた画像で、従来は専用の画像処理が必要だった。VLM なら画像を渡すだけで読める点が「生成AIの必然性」。
- **注意**: 画像の細部（示度の数字、前線の位置など）を**もっともらしく読み違える**ことがある。そのため、ラベルの許可リスト・季節整合・数値引用チェック・実況突合・予報突合のガードレールで出力を検証している（→ [validate.py](validate.py)）。

## 結論（先に）
| 問い | 結果 |
|---|---|
| 気象庁の天気図・衛星を自動で取れるか | **できた。** 認証なし・bosai の JSON/PNG/タイルのみ。ファイル名から対象時刻も取れ、衛星・アメダスを天気図に時刻合わせできる |
| VLM が天気図から気圧配置を読めるか | **読めた。** 高気圧・低気圧・停滞前線・台風の位置と移動方向、示度を読み取り、府県予報の概況と矛盾なし |
| ガードレールは機能するか | **機能した（合成テスト 3/3）。** ただし最初は 2/3 で、「許可リスト内の季節外れラベル（9月に冬型）」を見逃した → 季節整合ルールを追加して解消 |
| 実際の Claude API 呼び出しでも同様に読めるか | **読めた。** `vlm_read.py` を実行 → ガードレール検証 NG 0件/注意2件（低気圧・台風への言及有無の差異のみ）。**コスト $0.018/回**（Sonnet 5・入力4,615/出力883トークン） |
| 多数事例（型の違う過去日）での正答率は | **15事例で67%（10/15）。** 気象庁「日々の天気図」アーカイブ（2002年8月〜）から冬型・南岸低気圧・梅雨前線・太平洋高気圧・台風・移動性高気圧・日本海低気圧の7パターンを抽出して検証（→ [eval_historical.py](eval_historical.py) / [結果](#複数事例での正答率検証)）。**コスト合計 $0.065**（15回） |
| GO/NO-GO | **一部GO。** 取得〜VLM呼び出し〜検証まで実コードで通しで成立。**正答率67%（n=15）** — 台風・梅雨前線・移動性高気圧は強いが、低気圧の地域型（日本海低気圧⇄南岸低気圧）を系統的に混同する弱点あり |

## 構成
| ファイル | 役割 |
|---|---|
| [fetch_chart.py](fetch_chart.py) | 地上天気図（アジア/日本近海）・ひまわり赤外(B13、Natural Earth海岸線オーバーレイつき)・アメダス主要8地点・府県予報概況を取得 |
| [vlm_read.py](vlm_read.py) | Claude API（Sonnet 5）へ画像＋実況・予報を渡し、構造化出力を得る。`.env` の `ANTHROPIC_API_KEY` を使用 |
| [validate.py](validate.py) | ①ラベル許可リスト ②季節整合 ③確信度 ④数値引用 ⑤実況突合 ⑥予報突合。`--selftest` で壊した出力の検出を確認 |
| [fetch_hibiten.py](fetch_hibiten.py) | 気象庁「日々の天気図」（月次PDF、2002年8月〜）から指定日の天気図だけを機械的に切り出す。正解ラベル（見出し）付きの過去事例を作る |
| [eval_historical.py](eval_historical.py) | 複数の過去事例（天気図のみ、実況・予報なし）でVLMに気圧配置を判定させ、見出しベースの正解ラベルと突き合わせて正答率を出す |
| [daily_update.py](daily_update.py) | 上記を毎日1回通しで実行し、`webui/history/` に保存（GitHub Actionsから実行） |
| [coastline_ea.json](coastline_ea.json) | 東アジア域の海岸線データ（Natural Earth 1:50m、パブリックドメイン） |
| [CHARTS.md](CHARTS.md) / [images/](images/) | 使った画像（気象庁）と、その読み取り結果・実況予報との突合の解説 |
| [webui/](webui/) | デモUI（Vanilla JS）。日付選択で自動更新履歴を切替表示 |

実行:
- 当日1事例: `python fetch_chart.py` → `python vlm_read.py data/<対象時刻UTC>` → `python validate.py data/<対象時刻UTC>/vlm_output_api.json data/<対象時刻UTC>`
- 過去事例で正答率測定: `python fetch_hibiten.py <year> <month> [day]` → `python eval_historical.py`
- 毎日の自動更新と同じ処理を1回: `python daily_update.py`
（`data/` は git 除外）

## 取得元（入手性 / ライセンス / 粒度 / 遅延）
| データ | URL 系統（`https://www.jma.go.jp/bosai/`） | 粒度・遅延 |
|---|---|---|
| 地上天気図 | `weather_map/data/list.json` → `weather_map/data/png/<ファイル名>` | 日本近海 3時間毎(実測は約2時間遅れで掲載)、アジア 6時間毎。PNG 約600px |
| ひまわり赤外 | `himawari/data/satimg/targetTimes_fd.json` → `.../{base}/fd/{valid}/B13/TBB/{z}/{x}/{y}.jpg` | 10分毎、遅延は数分。`jp` 域は斜めに欠けた範囲で太平洋側が空白になるため `fd` の z=4 タイルを使う |
| アメダス | `amedas/data/map/{YYYYMMDDHHMMSS(JST)}.json` | 10分毎。値は [値, 品質] 形式 |
| 府県予報概況 | `forecast/data/overview_forecast/{office}.json` | 日3回程度 |
| 日々の天気図（過去、月次PDF） | `https://www.data.jma.go.jp/yoho/data/hibiten/{年}/{年下2桁}{月2桁}.pdf` | 2002年8月〜。1ページ4x4グリッド、各セルに天気図＋気象庁予報官が書いた見出し・解説。標準版PDF |
入手性は認証不要。ライセンスは気象庁HP利用規約に従う（出典明記）。「日々の天気図」は個人の研究用途で利用（商用・大量再配布はしない）。衛星画像の海岸線は Natural Earth 1:50m coastline（パブリックドメイン、naturalearthdata.com）。

## 複数事例での正答率検証
天気図単体（実況・予報なし）で気圧配置を当てられるかを、7パターン×15事例で測定。正解ラベルは気象庁「日々の天気図」の見出し（予報官が書いた要約）から、[validate.py](validate.py) の許可リストに一致するものだけを機械的に採用（曖昧な見出しは除外）。

**結果: 正答 10/15（67%）、コスト合計 $0.065**（`claude-sonnet-5`, `effort=low`）

|---|---|---|---|---|---|
| 2025-12-04 | 冬型 | 冬型 | 0.6 | 冬型の気圧配置 | OK |
| 2025-12-31 | 冬型 | 冬型 | 0.75 | 冬型の気圧配置 | OK |
| 2026-01-08 | 冬型 | 日本海低気圧 | 0.55 | 冬型の気圧配置が強まる | NG |

| 2025-12-14 | 南岸低気圧 | 南岸低気圧 | 0.6 | 南岸低気圧が発達 | OK |
| 2025-06-22 | 梅雨前線 | 梅雨前線 | 0.75 | 梅雨前線停滞 | OK |
| 2025-06-24 | 梅雨前線 | 秋雨前線 | 0.75 | 梅雨前線停滞 | NG |

**分かったこと**:
- **台風・梅雨前線・移動性高気圧は強い**（台風3/3、梅雨前線1/2、移動性高気圧2/2）。特徴的な渦・停滞前線・高気圧の縁取りが読み取りやすいためと考えられる。
- **「日本海低気圧」を2/2とも「南岸低気圧」に誤答**（系統的な混同）。低気圧の存在自体は検出できているが、日本海側か南岸側かという**地域の判定を間違えやすい**。
- **6月のデータを「秋雨前線」と誤答**（確信度0.75の高確信度エラー）。[validate.py](validate.py) の季節整合ルール（秋雨前線は9〜11月のみ許可）に通せば、この誤答は機械的に弾ける — **単発の確信度チェックだけでなく季節整合ガードレールが実際に効く**具体例。
- **確信度は弱いが手がかりになる**: 正答時の平均確信度 0.72、誤答時 0.61。ただし正答でも0.6のケース、誤答でも0.75のケースがあり、確信度だけでは判別しきれない。
- サンプルが少ない（各パターン1〜4事例）ため、正答率67%は粗い推定値。特に「日本海低気圧」は2/2とも同じ誤り方をしており、系統的な弱点の可能性が高い。

## 発見・注意
- **実況の時刻ずれ**: 最初は最新アメダス（15時JST）と天気図（12時JST）を混ぜていた。時刻合わせが必須で、`fetch_chart.py` は天気図の対象時刻を基準に統一済み。
- **許可リストだけでは足りない**: ラベルの形式チェックと「中身の妥当性」は別。季節整合のような外部知識ルールが要る。
- 設計書の「数値は実況JSONから引用」は、**天気図上の示度（hPa）には適用できない**（アメダスに無い値）。示度は `chart_values` に分離し、要目視確認 or 別途 OCR/突合が必要。

## 限界（過大評価しないために）
1. **当日1事例（実況・予報つき）は「秋の穏やかな日」で難易度は低い**。多数事例検証（15件）は天気図単体（実況・予報なし）なので、両者を単純に足し合わせて評価できない。
2. **正解ラベルが「気象庁の見出し」由来**。予報官の一言要約であり、気象学的に唯一の正解ではない（例: 複数パターンが同時に存在する日をどちらか一方に丸めている）。
3. **サンプル数が少ない**（1パターンあたり1〜4事例）。67%という数字の信頼区間は広い。
4. **天気図単体のみ**（衛星・実況・予報なし）。当日の実況突合・予報突合のガードレールは、過去事例では使えない（bosaiに過去実況アーカイブがないため）。
5. `validate.py` の数値引用チェックは文字列の部分一致で甘い（短い数字は誤って通りうる）。突合の合成テストも自作で、実 VLM の誤りの型を網羅していない。
6. 赤外画像の雲の解釈（帯状雲＝前線等）は目視のみで、定量評価していない。

## 次にやるなら
1. **「日本海低気圧⇄南岸低気圧」の系統的な誤答**への対処: アメダス実況（どの地域で風が強い/雨が降っているか）を渡せば区別しやすくなるか検証（過去実況は気象庁「過去の気象データ・ダウンロード」obsdlで代替可能）。
2. サンプル数を増やす（特に日本海低気圧・南岸低気圧・秋雨前線・太平洋高気圧を各5件以上）と、67%という数字の精度が上がる。
3. 数値引用チェックを単語境界つきの厳密一致に、示度はOCR or 目視サンプリングで誤読率を測る。
4. 教材モード（クイズ）は未着手。読者切替（一般/こども）はwebui・daily_update.pyで実装済み。
